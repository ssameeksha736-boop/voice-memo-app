# Reel — Voice Memo App with Transcription & Auto-Summary

A browser-based voice memo studio: record audio straight from the browser
(or upload a file), get a live transcript for free via the browser's own
Web Speech API, and get an automatic extractive summary computed by a
transparent PHP scoring algorithm — all while a Super Admin oversees
platform usage without ever seeing a user's actual memo audio, transcript,
or summary.

## 1. Overview & Objective

Voice memo apps typically either bolt on a paid speech-to-text API or skip
transcription entirely. Reel takes a middle path that fits this suite's
local-only, no-paid-API deployment scope: transcription runs entirely in
the user's browser via the built-in Web Speech API while recording (free,
no server round-trip, Chrome/Edge), and the transcript is then summarized
server-side by a classic, fully-explainable word-frequency extractive
algorithm written in plain PHP — not a trained model or an external AI
call. A Super Admin can manage accounts and see platform-wide usage, but
every query behind their screens is written to never select memo audio,
transcript, or summary content, so oversight never comes at the cost of a
user's privacy over what they actually recorded.

## 2. Tech Stack

- **Backend**: Plain PHP 8.1+ (custom MVC, no framework) — PDO/MySQL, native sessions
- **Frontend**: Tailwind CSS (via CDN + inline config), "Studio dark" theme
  (near-black + violet, waveform motif) — vanilla JS for the recording deck
  (`assets/js/recorder.js`: MediaRecorder, Web Speech API, Web Audio
  AnalyserNode-driven waveform canvas) and small shared UX touches
  (`assets/js/main.js`)
- **Database**: MySQL/MariaDB (InnoDB, foreign keys enforced)
- **Server**: Apache via XAMPP, or PHP's built-in server for local testing
- **Browser APIs used** (no external service, no API key, no cost):
  MediaRecorder (audio capture), Web Speech API / `SpeechRecognition`
  (live transcription, Chrome/Edge only), Web Audio API `AnalyserNode`
  (live waveform visualization)

## 4. Feature List

See `FEATURES.md` for the full persona-by-feature breakdown. In short:

- **User**: record memos in-browser with a live waveform + live transcript,
  or upload existing audio files; automatic extractive summary on save;
  full CRUD (edit title/folder/tags/transcript, delete); organize with

  dashboard (total memos, total recorded time, daily volume, source
  split); per-user activity overview (counts, total time, last activity —
  never memo content).

### The three non-obvious mechanics

**The summary is a classic extractive algorithm, not AI.**
`core/Summarizer.php` splits a transcript into sentences, builds a
word-frequency table over non-stopword tokens (normalized against the
most frequent word), scores each sentence as `sum(word frequency scores) /
sentence word count`, and keeps the top ~30% of sentences (clamped to
1–6) in their *original* reading order — not sorted by score, so the
summary still reads as a coherent excerpt. This is a documented
simplification (a small variant of Luhn's 1958 method): it has real,
explainable limitations — no coreference resolution, no topic modeling,
a word outside the frequency table contributes nothing. It runs entirely
offline in PHP with zero external dependency, and every seeded `summary`
in `schema.sql` was generated by actually running this algorithm against
the seeded `transcript`, not hand-written.

**Live transcription is the browser's job, not the server's.**
`assets/js/recorder.js` uses the Web Speech API (`SpeechRecognition` /
`webkitSpeechRecognition`) while `MediaRecorder` is capturing audio,
appending each final result to a live transcript box the user can edit
before saving. This only works in Chromium-based browsers (Chrome, Edge)
with a live microphone stream — it cannot transcribe an already-recorded
file, so uploaded memos (and any unsupported browser) fall back to a
manually-typed/pasted transcript. The page detects and displays this
limitation rather than failing silently.

**The Super Admin's oversight queries never touch memo content.**
`Memo::platformStats()`, `Memo::dailyVolume()`, and `Memo::statsForUser()`
explicitly select only counts, durations, and timestamps — `transcript`,
`summary`, and `audio_path` are never named in those SQL statements, so a
memo's actual content is structurally unreachable from the Super Admin's
screens, not just hidden by a UI field that a future change could
accidentally expose. This mirrors project #13 (Journal App)'s Wellness
Coordinator privacy pattern, applied here since memos are just as
personal as journal entries.

## 6. Setup Instructions

1. Copy the `voice-memo-app/` folder under XAMPP's `htdocs`, or serve it
   directly with PHP's built-in server (see below).
2. Start MySQL/MariaDB. On this suite's reference machine, MariaDB
   listens on the default **port 3306** — see the top-level
   `CLAUDE.md` for why. Adjust `config/database.php` if your MySQL is on a
   different host/port.
3. Import the schema (creates the database, tables, and demo seed data):
   ```
   mysql -u root -P 3306 < database/schema.sql
   ```
   or import `database/schema.sql` via phpMyAdmin.
4. Serve the app. From the project folder:
   ```
   php -S localhost:8014 -t public public/index.php
   ```
   (`-t public` matters — without it, static assets under `public/assets`
   and `public/uploads` 404 while the HTML still renders, since the
   built-in server's document root defaults to the directory PHP was
   launched from otherwise.)
5. Visit `http://localhost:8014/index.php?route=login` and sign in with
   any of the demo credentials above.
6. **Recording requires a secure context.** Browsers only grant
   microphone access (`getUserMedia`) on `https://` or `http://localhost`
   — `http://localhost:8014` satisfies this, but if you instead browse to
   a LAN IP or a non-localhost hostname, recording will be blocked by the
   browser even though the rest of the app works fine. Use Chrome or Edge
   to see live transcription; other browsers can still record and upload,
   just without the live transcript.

This project has no `composer.json` — every dependency (Tailwind, Google
Fonts, all recording/transcription logic) is either a CDN `<script>` tag
or a native browser API, so there's no `composer install` step.

## 8. Anticipated Viva Questions

**Is the transcription "real" speech recognition, or faked?**
It's real, but it's the *browser's* speech recognition, not a server-side
or paid one. `SpeechRecognition` (the Web Speech API) is a built-in
Chromium capability that streams microphone audio to the browser vendor's
own recognition engine and returns text — Reel just listens for its
`result` events and appends them to an editable transcript box while
`MediaRecorder` captures the actual audio in parallel. This is why it only
works in Chrome/Edge with a live microphone: it's not something this
project's PHP backend does or could reproduce for an uploaded file, which
is why uploads fall back to a manually-typed transcript.

**Is the auto-summary "real" AI?**
No, and the README says so plainly. `core/Summarizer.php` is a fixed,
documented word-frequency / sentence-scoring heuristic — count
non-stopword tokens, score sentences by their words' relative frequency
divided by sentence length, keep the top-scoring ~30% in original order.
It has real, explainable limitations: it can't detect that two sentences
mean the same thing, can't follow pronouns back to what they refer to, and
a topically-important sentence using only rare words scores low. It was
chosen deliberately over a trained model or an external AI API because (a)
this suite's deployment scope is local-only with no internet dependency
assumed at demo time, and (b) a transparent, inspectable scoring rule —
one an examiner can trace by hand on a short transcript — is easier to
defend in a viva than a black-box model would be. The memo detail page's
"How was this summary generated?" panel exists specifically to make this
demonstrable live.

**How is memo privacy actually enforced, not just hidden in the UI?**
Structurally, at the query level — the same pattern as project #13
(Journal App). `Memo` has two families of methods: user-facing ones
(`find()`, `byUser()`) that `SELECT *` and therefore include `transcript`/
`summary`/`audio_path`, used only on routes gated by
`Auth::requireRole('user')` and scoped to `Auth::id()`; and
Super-Admin-facing ones (`platformStats()`, `dailyVolume()`,
`statsForUser()`) that explicitly list only counts, durations, and
timestamps and never mention those three columns at all. Since the data
simply isn't fetched into PHP on the admin's code path, there's no way for
a future admin-view bug to leak memo content — it was never in memory to
leak.

**Why store the summary instead of recomputing it on every read?**
Recomputing on every memo-list render would be wasteful, and would
silently change a memo's historical summary if the scoring algorithm is
ever tuned later — freezing the summary at save/edit time keeps a memo's
history stable and matches what the user actually saw when they saved it
(same rationale as project #13's stored `sentiment_score`). The *full
scoring breakdown* behind that stored summary, though, is intentionally
NOT stored — it's recomputed live from the transcript every time the
explainability panel is opened, so it can never drift out of sync with
the transcript it's explaining.

**Why two separate file input names (`audio_recorded` / `audio_uploaded`)
instead of one?**
Two `<input type="file">` elements sharing the same `name` in one
multipart form is inconsistent across browsers and PHP's `$_FILES`
parsing — only one is reliably visible server-side, and which one is
undefined. Since only one of the two tabs is ever actually submitted, using
two distinct names and having `UserController::store()` pick the right
`$_FILES` key based on the posted `source` field avoids that ambiguity
entirely, at zero cost to the user experience.

**How are passwords and CSRF handled?**
`password_hash()`/`password_verify()` (bcrypt), never plaintext. Every
state-changing form carries a per-session CSRF token verified via
`Csrf::requireValid()` before anything touches the database — a forged
POST without a valid token gets rejected with HTTP 419 (verified live
during testing). Login regenerates the session ID
(`session_regenerate_id(true)`) to prevent session fixation. Every
controller action that isn't public starts with an `Auth::requireRole(...)`
call, so a User session hitting an admin-only URL directly is rejected
server-side (HTTP 403, verified live) rather than just missing the nav
link in the UI, and a deactivated account is rejected at login (verified
live with the seeded inactive user).

**How are uploaded audio files validated?**
`core/Upload.php` checks the file's *real* MIME type via PHP's `finfo`
extension (sniffing actual file bytes, not trusting the client-supplied
`Content-Type` header) against an allow-list (webm/ogg/mp3/wav/m4a/aac),
enforces a 25MB size cap, and stores it under a random 32-character
filename — never the client's original filename — to avoid overwrite and
path-traversal risk. A file that fails MIME sniffing (e.g. a `.txt`
renamed to look like audio) is rejected server-side; verified live during
testing with a plain-text file disguised as `audio/wav`.

**One real bug was found and fixed during this testing**: viewing a memo
with a `NULL` transcript (e.g. an uploaded memo nobody typed a transcript
for) threw a `TypeError` in `UserController::viewMemo()`, because
`$memo['transcript'] !== ''` is `true` for `null` (a strict comparison,
not an emptiness check), which then passed `null` into
`Summarizer::analyze(string $transcript)`'s typed parameter. Fixed by
switching the guard to `!empty($memo['transcript'])`, which correctly
treats both `NULL` and `''` as "nothing to summarize." Confirmed fixed by
re-requesting the same memo and seeing the correct empty-state render
instead of the HTTP 500 page.

**Issue #34 fix (unauthenticated audio access + array-typed field crash)**:
a repo-wide sweep found that memo audio was served as a plain static file
under `public/uploads/memos/<random>.<ext>`, linked directly from
`<audio src="/uploads/...">` — reachable by anyone with or guessing the
URL, no session/ownership check at all, unlike every DB-backed memo action.
Separately, `AuthController::login()`'s `trim($_POST['email'] ?? '')` and
the `e()`/`old()` helpers in `core/helpers.php` had no scalar-type guard,
so an array-typed field (e.g. `transcript[]=x` on
`user/memos/summarize-preview`) threw an uncaught `TypeError`, caught only
by the router's generic 500. Fixed by:
- Adding an authenticated `GET user/memos/audio?id=` route
  (`UserController::audio()`) that calls `Memo::find($id, Auth::id())` to
  verify ownership before `Upload::streamMemoAudio()` streams the file;
  `memo_view.php`'s `<audio src>` now points at this route instead of the
  direct path. Added `public/uploads/.htaccess` (`Require all denied`) as
  defense in depth under a real Apache deployment, since the app no longer
  needs to link to that directory directly.
- Guarding `e()`/`old()` in `core/helpers.php` against non-scalar input
  (a value that isn't `is_scalar()` renders as `''` instead of throwing),
  and adding a small `str_field()` helper used at every raw
  `trim($_POST[...] ?? '')` / `trim($_GET[...] ?? '')` call site in
  `AuthController::login()` and `UserController` (`store`, `update`,
  `summarizePreview`, `star`, `folderStore`, and the `memos()` filter list)
  so a client submitting any of those fields as an array is treated as an
  empty/default value instead of crashing the request.

### Second review pass (2026-09-12) — five bugs found and fixed

Re-audited against the suite-wide bug classes in `REVIEW-LOG.md`, verified
against the real MariaDB seed data. All five were reachable by normal
clicking, not crafted requests:

1. **Saving a memo redirected to a 404.** `redirect()` built
   `/index.php?route=user/memos/view?id=7` — the *second* `?` is a literal
   character, so PHP parsed one parameter `route=user/memos/view?id=7` and
   `$_GET['id']` never existed. Creating a memo, saving an edit, and
   starring from a memo's detail page all dropped the user on "Not found"
   even though the write had succeeded. `redirect()` now splits the route
   from its query and rejoins with `&`.
2. **The stored summary and the explainability panel could disagree.** The
   "under 12 words → keep the whole transcript" rule lived only in
   `Summarizer::summarize()`, while the panel and the live "Preview
   summary" button both call `Summarizer::analyze()`, which had no such
   rule. For a short multi-sentence transcript the Summary card showed all
   three sentences, the panel highlighted one and claimed those highlighted
   rows produced the summary above, and the pre-save preview showed a third
   answer. The threshold now lives inside `analyze()` as the single
   authority, `summarize()` is a pure delegation, and the panel explains
   the full-text fallback instead of contradicting it.
3. **A deactivated account kept working until logout.** `Auth::requireLogin()`
   trusted the session and never re-read `users.status`, so a Super Admin
   deactivating someone mid-session changed nothing until they happened to
   log out. Status (and role) are now re-read once per request and a
   deactivated session is force-logged-out with an explanatory message.
4. **The login page never rendered error flashes** (only `success`), so the
   message from #3 would have been set and silently discarded.
5. **Tag creation had a race.** `tags.name` is UNIQUE and shared
   platform-wide; two users saving memos that introduce the same new tag at
   once both missed on the SELECT, and the loser's INSERT threw an uncaught
   duplicate-key error — surfacing as a blank HTTP 500 *after*
   `Memo::create()` had already inserted the memo. The user was told the
   save failed when it had actually succeeded. `Tag::findOrCreate()` now
   catches the duplicate and adopts the winner's row.

Also re-confirmed unchanged: the Super Admin privacy guarantee still holds
(comment-stripped scan of `Memo`'s admin-facing methods finds no
`transcript`/`summary`/`audio_path`/`SELECT *`; rendered admin pages
contain 0 of 19 seeded transcript fragments and 0 of 19 summary fragments,
against a positive control proving the probe finds that text on the
owner's own pages); cross-user memo/folder access 404s; CSRF returns 419;
role enforcement 403s both directions; deleting a folder still keeps its
memos (verified 7 → 7 with two moved to Unfiled); and the per-project
session cookie (`reel_voicememo_session`) now prevents the suite-wide
`PHPSESSID` collision when several projects are open at once.

**What was not exercised**: real device microphone recording, live
`SpeechRecognition` transcription, and the live waveform canvas — these
require an actual browser with mic access and cannot be driven by `curl`.
The client-side JavaScript (`assets/js/recorder.js`) was reviewed
carefully for correctness (element IDs cross-checked against
`memo_form.php`, DataTransfer-based file injection, tab-switching state,
mime-type fallback list) but should get a manual once-over in a real
Chrome/Edge browser before the viva to visually confirm the recording deck
UI and live transcript.

## 10. Recorder / summarizer flow (for a live viva walkthrough)

1. **New memo → Record tab**: tap the red button → browser asks for mic
   permission → `MediaRecorder` starts capturing audio while a
   `Web Audio AnalyserNode` drives the canvas waveform bars in real time →
   if Chrome/Edge, `SpeechRecognition` simultaneously streams a live,
   editable transcript into the box below.
2. **Stop**: the recorded `Blob` is packaged into a `File` and injected
   into a hidden `<input type=file name=audio_recorded>` via the
   `DataTransfer` API, so the normal multipart form submit picks it up
   exactly like a real file picker would — no custom AJAX upload code
   needed.
3. **Save**: `UserController::store()` validates the file's real MIME
   type/size (`Upload::storeMemoAudio()`), then computes
   `Summarizer::summarize($transcript)` and stores the memo row.
4. **View**: the memo detail page re-runs `Summarizer::analyze()` on the
   stored transcript on every view (not cached) to render the "How was
   this generated?" panel — per-sentence scores, which sentences were
   selected, and the top keyword frequencies behind them.
